## Key design decisions
- **Language policy (README §15.1)**: all code, DB fields, API, UI text, seed data, certificates in English.
- **`learning` schema** (exactly README §8.4): `courses, lessons, exercises, enrollments, practice_sessions, chat_messages, certificates`. UUID PKs, per-module Alembic migrations in `alembic/versions/learning/`.
- **`ai_chat` module**: owns the DeepSeek adapter + `POST /api/v1/ai/chat`; conversations persist in `learning.chat_messages`. System prompt enforces README §10.4 dialogue principles; answers return citations.
- **Cross-module seams (A's and C's modules don't exist yet)**:
  - `core/` auth: minimal placeholder register/login issuing HS256 JWTs (to be replaced by C's module)
  - `shared/coin_client.py`: coin transfer interface (`COURSE_UNLOCK` −10 user/+70% community/+30% platform, `REWARD_PRACTICE` +5) with a stub implementation; one-file swap to C's CoinService later; idempotency keys included
  - `shared/rag_client.py`: calls A's `POST /api/v1/rag/search` when available; until then serves license-tagged seed chunks so license/revocation filtering is real and demonstrable
- **DeepSeek**: real adapter; key read from `DEEPSEEK_API_KEY` in `services/api/.env`; API fails fast with a clear error if missing. Tests use a mocked adapter (no key needed).
- **API conventions (README §9)**: base `/api/v1`, Bearer JWT, `limit`/`offset` pagination, unified error body `{"error":{"code","message","details"}}`.

## Backend endpoints (README §7.2, exactly)
`GET /courses`, `POST /courses/{id}/enroll` (idempotent, coin debit), `GET /lessons/{id}` (enrollment-gated), `POST /practice/sessions`, `POST /practice/sessions/{id}/messages` (deterministic scoring for MCQ/fill-in, DeepSeek feedback for open-ended, REWARD_PRACTICE on completion), `POST /certificates/claim` (100% progress required), `GET /certificates/{code}/verify` (public), `POST /ai/chat` (RAG-filtered context + DeepSeek + citations).
